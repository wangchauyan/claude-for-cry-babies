title: "5.2 萬用修復三步驟"
---


不管遇到哪種錯誤，這三步都能用。背下來，你就有了 AI 急救包。

## Step 1：截圖或複製錯誤訊息

如果 Artifacts 面板顯示紅色錯誤訊息：

1. 看看面板裡有沒有「Show Error」或類似的按鈕，點開它
2. 把整段紅色文字**全部複製**（不需要看懂）
3. 如果沒有文字，就截圖

**重要**：就算你完全看不懂那段錯誤訊息也沒關係。你不需要看懂，Claude 看得懂就行。

## Step 2：丟回去 + 說明你期望的行為

把錯誤訊息貼回對話框，加上你的描述：

> 「剛才的 Artifacts 出錯了，錯誤訊息如下：
>
> ```
> [貼上錯誤訊息]
> ```
>
> 我期望的行為是：按下『送出』按鈕後，應該要在下方顯示結果。但現在按下去什麼都沒反應。
>
> 請修好它。」

注意兩個關鍵：
- **貼上完整的錯誤訊息**（不要自己摘要，可能會漏掉重要資訊）
- **描述你期望的行為**（Claude 需要知道「正確的樣子」是什麼）

## Step 3：如果修不好 → 叫它砍掉重練

如果 Claude 修了一版但還是不對，別陷入「修 → 又錯 → 再修 → 又錯」的循環。超過三次修不好，直接說：

> 「這個方向好像行不通。請**不要修改現有的程式碼**，用全新的思路從頭重新做一個。需求跟之前一樣：[再描述一次你要什麼]。」

有時候，從零開始比在錯誤的基礎上修修補補更有效率。

## 真實的 Debug 對話（一步步來）

上面的三步驟聽起來很簡單，但實際操作長什麼樣？讓我們走一遍完整的 debug 流程。

### 情境

你請 Claude 做一個小費計算器。看起來很棒——有帳單金額輸入框、小費百分比滑桿、還有顯示總額的地方。

但是當你輸入 50 元、滑桿拉到 20%，總額顯示的是 **「$NaN」** 而不是 **「$60.00」**。

你不知道 NaN 是什麼。沒關係，你不需要知道。

### 步驟 1：用你自己的話描述發生了什麼

直接跟 Claude 說：

> 「小費計算器看起來不錯，但有個問題。我在帳單金額輸入 50，小費滑桿調到 20%，總額那邊應該顯示 $60，但它顯示的是 '$NaN'。這是什麼意思？可以修好嗎？」

注意你做了什麼：
- 說了你做了什麼動作（輸入 50、滑到 20%）
- 說了你看到什麼（$NaN）
- 說了你期望看到什麼（$60）

### 步驟 2：Claude 的回應

Claude 會解釋：「NaN 代表 'Not a Number'，問題出在程式碼把你輸入的值當成文字字串而不是數字來處理，所以計算出了錯誤結果。我已經修好了，現在它會正確地把輸入轉換成數字再做計算。」

修好了。你試一下，50 元 + 20% 小費，正確顯示 $60.00。

### 步驟 3：多想一步——邊界情況

但聰明的你可能會想：「那如果有人亂輸入呢？」

> 「基本計算正常了，謝啦。但你能幫我測試一下邊界情況嗎？比如說——如果帳單金額留空白會怎樣？如果有人輸入文字而不是數字呢？」

Claude 會加上輸入驗證：空白時提醒「請輸入金額」，輸入文字時顯示「請輸入有效數字」。

### 用白話說，剛剛發生了什麼

你不需要懂 NaN 是什麼。你不需要懂 JavaScript。你不需要懂什麼叫「型別轉換」。

你做的事情只有三件：
1. **用你自己的話描述問題**——「我做了 A，看到 B，但應該是 C」
2. **說明你期望的行為**——正確的樣子長怎樣
3. **請 Claude 想想你沒想到的情況**——邊界情況

就這樣。這個流程適用於任何 bug，不管它多複雜。

### 永遠有效的 Debug 萬用句

把這張表存起來，遇到問題直接套用：

| 問題類型 | 你可以這樣說 |
|---------|------------|
| 顯示錯誤數據 | 「當我做 [動作]，它顯示 [錯的]。它應該顯示 [對的]。」 |
| 按鈕沒反應 | 「[按鈕名稱] 按了沒反應，什麼都沒發生。」 |
| 排版壞掉 | 「[某元素] 跟 [另一個元素] 重疊了，可以修一下間距嗎？」 |
| 改了東西後壞了 | 「你加了 [新功能] 之後，[舊功能] 壞了。可以修好 [舊的] 但不要拿掉 [新的] 嗎？」 |
| 完全不知道哪裡壞了 | 「好像有什麼地方不太對但我不確定是什麼。你能檢查一下程式碼有沒有常見問題嗎？」 |

不需要懂技術術語。用你的話說就對了，Claude 聽得懂。
